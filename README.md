# jmporch.com

The existing [jmporch.com](https://jmporch.com) portfolio, migrated to Zola with
editable content, the original desktop design, responsive repairs, and vanilla
JavaScript. Images, icons, and the existing Josefin Slab font are served locally.
The published site has no JavaScript package or external font dependencies.

## Preview and build

The project pins **Zola 0.23.6** and uses **Python 3.11 or newer** to generate the
portfolio RSS feed from Git history. Both are build tools; the published website
needs neither. No Python packages, Node.js, npm, or Rust toolchain are required.

```sh
bash scripts/install-zola.sh
python3 scripts/site.py serve
```

Open the URL printed by Zola (normally `http://127.0.0.1:1111`). Changes to content,
templates, styles, and portfolio data rebuild automatically. Use `scripts/site.py`
for builds and previews so the portfolio feed stays up to date. The installer downloads the official
binary to `.cache/bin` and verifies its pinned SHA-256 checksum. You can instead
install the same Zola version yourself; the wrapper finds it on your PATH, or
accepts `--zola /path/to/zola`.

```sh
python3 scripts/site.py check --skip-external-links
python3 scripts/site.py build
python3 -m unittest discover -s tests -v
python3 scripts/verify_site.py --zola .cache/bin/zola
```

Build output is in `public/`, which is ignored by Git. That directory can also be
copied to an ordinary static webserver.

## Update the content

| Content | File |
| --- | --- |
| About text | `content/about.md` |
| Work experience | `content/work/*.md` |
| Education | `content/education/*.md` |
| Portfolio links and categories | `data/portfolio.toml` |
| Navigation, contact links, résumé location | `data/navigation.toml` |
| Site title, description, name | `zola.toml` |
| Images, résumé, and other downloads | `static/content/` |

Edit Markdown below the `+++` metadata delimiters. Content-only changes do not
require editing the page templates. The `[extra]` dates field supplies the date
label for work and education entries.

To add a job or education entry, copy a neighboring `.md` file, edit its title,
dates and body, then add its content-relative path to the `extra.entries` list in
that directory's `_index.md`. The list controls display order. These entries have
`render = false` because they are embedded in the homepage; Zola excludes such
pages from normal section page lists, so they are loaded explicitly by path.
Selected raw HTML preserves the original custom list and citation markup.
Links to homepage panels in these embedded files use `<a href="#portfolio">`
because the target exists in the final homepage template, not the Markdown file.

## Add a portfolio item

Add an entry under the appropriate group in `data/portfolio.toml`:

```toml
[[groups.items]]
id = "my-new-article"
label = "My New Article | <cite>Publication Name</cite>"
url = "https://example.com/my-new-article/"
description = "An optional introduction for RSS readers."
```

Use a unique lowercase ID with hyphens and keep it when changing the title, URL,
or category. No date is required. The build finds the first commit introducing
that ID and uses its committer timestamp as the date added to the portfolio.
This represents the portfolio announcement, not the external publication date.
The RSS identifier is derived from the stable ID, so edits and later builds do
not turn an old item into a new announcement. Reusing a removed ID retains its
original date; genuinely new work should have a new ID.

The generated `/feed.xml` contains every linked portfolio item. It sorts additions
newest first and uses the current TOML order for items added in the same commit.
Before committing, a new item previews first with its RSS date omitted; committing
gives it a reproducible timestamp. The page retains its manually arranged groups.

The 20 original feed entries retain their `feed_date`, `feed_title`, `guid`, and
description in the same TOML file. Three existing items with no known date use
`legacy_undated = true` and appear at the end in file order without invented dates.
These migration fields are unnecessary for new entries. The page's explanatory
note is not a feed item.

`scripts/site.py` generates `static/feed.xml` before invoking Zola, which copies
it into `public/`. The generated XML is ignored by Git and should not be edited.
Preview mode also refreshes it when portfolio data or HEAD changes. Builds require
a Git checkout with full history; shallow clones fail with a clear message instead
of silently assigning incorrect dates. GitHub Actions uses `fetch-depth: 0`.
The blog's separate `/blog/atom.xml` feed is still generated by Zola from posts.

## Add a blog post

Create `content/blog/my-post.md`:

```markdown
+++
title = "My post"
date = 2026-10-14
description = "A short description for the blog index."
draft = true
+++

Write the post in **Markdown**.
```

Preview unpublished work using `python3 scripts/site.py serve --drafts`. Set `draft = false`
or remove that line to publish it on the next deployment. Every post must have a
date. Its filename supplies the slug: the example becomes `/blog/my-post/`.
Keep that slug stable when changing the title to preserve incoming links.

The blog automatically generates individual pages, newest-first listings,
pagination (10 posts per page), older/newer links, and `/blog/atom.xml`.
The sidebar's Blog link appears once there is a published post. No sample posts
are published. `/blog/` currently displays an empty-state message.

For images belonging to a post, use `content/blog/my-post/index.md` with image
files beside it and relative Markdown image references.

## Deployment

The default branch is **main**. Pushes and merged pull requests deploy automatically:

| Branch | Destination | Workflow |
| --- | --- | --- |
| `main` | Production at `https://jmporch.com` | `.github/workflows/production.yml` |
| `staging` | [GitHub Pages](https://jporch.github.io/jmporch.com-static/) | `.github/workflows/pages.yml` |

Merge experimental changes into `staging` to preview them, then merge the changes
you want to publish into `main`. Pull requests run checks without deploying.
Both workflows also accept manual runs; deployments are restricted to their
respective branches.

Each workflow uses official GitHub Actions pinned to immutable commits, installs
the checksum-verified Zola version, validates generated local links and assets,
and exercises a temporary 12-post blog to check navigation, pagination, feeds,
and draft exclusion. Feed tests use temporary Git repositories to check addition
dates, edits, URL changes, moves, same-commit ordering, and stable identities.
Temporary test posts never enter the deployment artifact.
Only the deployment job receives Pages write and OIDC permissions.

In GitHub **Settings → Pages**, select **GitHub Actions** as the publishing source.
The workflow reads the configured Pages URL and passes it to Zola, so assets work
under the `/jmporch.com-static/` project path and after a future domain change.
Pages remains the staging site; production builds use `https://jmporch.com`.

### Production server

The `production` GitHub environment permits deployments from `main` only. It holds
the `SSH_PRIVATE_KEY` secret and these variables:

| Variable | Value |
| --- | --- |
| `SSH_HOST` | `jmporch.com` |
| `SSH_PORT` | `22` |
| `SSH_USER` | `jmporch-deploy` |
| `SSH_KNOWN_HOSTS` | Server's verified ED25519 public host key in known_hosts format |

The server host key was checked against the fingerprint supplied through a trusted
server session. Update the pinned key deliberately if the server changes.
The private deployment key must be unencrypted and match the public key installed
for the unprivileged deployment account.

Install `rsync` on Ubuntu (`sudo apt install rsync`). The deployment account must
own `/srv/jmporch-deploy/releases/current`, or have permission to create it under
`/srv/jmporch-deploy/releases`. These paths must be real directories. NGINX needs
read/traverse access; uploaded directories and files use modes 755 and 644.

Set the existing NGINX site's document root, preserving its domain and TLS settings:

```nginx
root /srv/jmporch-deploy/releases/current;
index index.html;

location / {
    try_files $uri $uri/ =404;
}
error_page 404 /404.html;
```

After changing the configuration, run `sudo nginx -t` and
`sudo systemctl reload nginx`. Deployments do not need sudo or an NGINX reload.

The production job uploads the checked artifact over SSH and verifies its contents
with a second checksum comparison. It synchronizes directly into
`/srv/jmporch-deploy/releases/current`, removing files there that are absent from
the new build. Keep server-only files outside that directory. There are no saved
releases or automatic backups. Transfers use delayed updates, but the whole site
does not switch atomically; a deployment can briefly serve mixed versions.
To roll back, revert the relevant commit on `main` and redeploy.

`https://jmporch.com/deployment.json` identifies the deployed source commit once
NGINX serves this directory. A successful upload alone does not change NGINX's root.

## Design and behavior

`static/style.css` is the original stylesheet. `static/enhancements.css` contains
the local font, accessible button styles, and responsive fixes. Templates retain
the original section IDs, CSS classes, four-panel homepage, and content wrappers;
collapsible headings now contain keyboard-accessible native buttons.

`static/main.js` handles hash navigation, browser back/forward, collapsible entries,
and the mobile menu, including eased opening/closing, breakpoint changes and Escape. Content remains
readable if JavaScript is disabled. Reduced-motion preferences are respected.

The mobile menu overlays the entire visible content area without moving the page,
locks background scrolling, and prevents keyboard focus entering covered content.
Its original header alignment and link spacing fit within a 320×568 viewport.
Narrow-screen fixes address
heading overflow, the image's doubled padding width, and menu button placement.
The malformed email address was corrected to `porchjm@gmail.com`. The original
wording, résumé, and portfolio destinations are preserved. The footer copyright
year is computed from the current UTC year each time Zola builds the site.

The portrait retains its original attribution. Josefin Slab's license is included
in `static/fonts/OFL.txt`; no new license is assigned to the owner's site content.
